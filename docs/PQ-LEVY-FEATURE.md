## 1. Why This Is the Number One Priority

PQ is the single biggest blocker before BoldMark can use this platform for billing. Every downstream finance workflow — levy generation, invoice line items, arrears tracking, reserve fund contributions — depends on each unit having a PQ value that drives its individual levy amount.

Justin's own words:
> *"If we could deal with the unit size, the rest is going to be easy... the main important thing is to invoice the people correctly."*
> *"If we could sort out the issue of the levy amount which is determined by the unit size, then we're going somewhere."*

## 2. Domain Knowledge — What PQ Is

### 2.1 South Africa — Sectional Title

PQ stands for **Participation Quota**. It is a legally assigned value under:
- Sectional Titles Act 95 of 1986
- Sectional Titles Schemes Management Act 8 of 2011

When a scheme is registered, a land surveyor measures every section (unit) and assigns each one a PQ based on its floor area relative to the total floor area of the entire scheme. PQ determines:

1. Each unit's proportional share of common property
2. Each unit's proportional share of all levy costs — larger unit, higher levy
3. Each unit's voting weight at trustee and AGM meetings

All PQs across a properly registered SA scheme sum to exactly **100**.

### 2.2 PQ vs Ratio — One Field, Two Representations

Justin confirmed: *"PQ and ratio is the same thing."*

WeConnectU stores both a rounded display value ("PQ") and a full-precision value ("Ratio 1"). We store **one field at full precision** (`pq` decimal 10 d.p.). The frontend rounds to 4 d.p. for display.

### 2.3 PQ Scales Linearly With Unit Size

- Unit 101: 134 m² → PQ `3.1076165908`
- Units 109–115: 35 m² each → PQ `0.8117085408`
- `134 / 35 = 3.828` and `3.1076 / 0.8117 = 3.828` ✓

### 2.4 Botswana — HOA Context

Botswana communities operate as Homeowners Associations. The practical levy mechanics are identical. We use the same `pq` field for both countries. The formula works whether PQs sum to 100 or not.

### 2.5 VOTE = PQ

In SA sectional title law, voting rights equal PQ exactly. We do not add a separate `vote` column.

## 3. Levy Types — The Full Picture

### Core Type 1 — Admin Fund Levy

Day-to-day running costs: management fees, insurance, security, cleaning, garden services, minor maintenance. Legally mandated for SA Body Corporates. HOA equivalent for Botswana. **PQ-distributed. Auto-generated by the billing engine.**

### Core Type 2 — Reserve Fund Levy

Future capital expenditure: roof, painting, lifts, driveways, infrastructure. SA law requires funding via a 10-year plan. Botswana equivalent: Sinking Fund. **PQ-distributed. Auto-generated by the billing engine.**

### Additional Line Items (not estate budgets)

| Charge | How set | Countries |
|---|---|---|
| CSOS Levy | Fixed per unit, configured per estate | SA only |
| Special Levy | Manual ad-hoc, per instance | SA + BWA |
| Water Recovery, Electricity, etc. | Metered per unit | SA + BWA |
| Insurance Excess, penalties, deposits | Manual one-off | SA + BWA |

The estate carries exactly two monetary budget fields: `admin_fund_amount` and `reserve_fund_amount`. Everything else is a line item.

## 4. Charge Types — Decisions

### 4.1 Codes Are Removed Entirely

Charge type codes (`LEVY`, `ADMIN_LEVY`, `ELECTRICITY_RECOVERY`, etc.) are removed from the database, the API, and the UI entirely.

**Why:** Codes are derived from the original name at creation and never updated. If a user renames "Electricity Recovery" to "Power Recovery", the code stays `ELECTRICITY_RECOVERY` — permanently misleading. The ID is the stable unique identifier the database and application need. The name is what users see. There is no scenario where a code adds value that the ID and name don't already cover.

**How the billing engine identifies system charge types without codes:** A hidden internal `type` column is added to `charge_types`. This column is never exposed in the API or UI. It has a fixed enum-backed value for system types (`admin_levy`, `reserve_levy`, `csos_levy`, `rent`) and is `null` for all user-created custom charge types. Unlike a code, `type` is never derived from name, never shown to users, and never goes stale.

### 4.2 The Complete System Charge Type Set

These four types are seeded for every organisation, locked (`is_system = true`), cannot be deleted:

| Type value | Name | Description | Recurring | Applies to | Auto-generated |
|---|---|---|---|---|---|
| `admin_levy` | Admin Fund Levy | Monthly admin fund, distributed by PQ | Monthly | Owner | Yes — billing engine |
| `reserve_levy` | Reserve Fund Levy | Monthly reserve fund, distributed by PQ | Monthly | Owner | Yes — billing engine |
| `csos_levy` | CSOS Levy | Mandatory government levy (SA). Amount set per estate. | Monthly | Owner | No — flat, per-estate config |
| `rent` | Rent | Regular monthly rental payment | Monthly | Tenant | No — flat per unit |

### 4.3 How ADMIN_LEVY and RESERVE_LEVY Work

Auto-generated on every billing run. Property manager never manually adds them — the billing engine reads `admin_fund_amount` and `reserve_fund_amount` from the estate, applies the PQ formula, and writes both as invoice line items.

### 4.4 How CSOS_LEVY Works

Legally required in SA, absent in Botswana. Not PQ-based — flat per-unit amount. The charge type record defines WHAT it is. The amount is configured per estate in the estate's charge type settings. When creating/editing an SA estate (`country = ZA`), the UI prompts the manager to configure the CSOS amount for that estate. No global amount on the charge type itself.

### 4.5 How SPECIAL_LEVY Works

Unchanged. Ad-hoc, manually entered amount, applied per instance.

### 4.6 Seeder Approach Without Codes

Since `code` no longer exists, `updateOrCreate` uses:
- System types: matched by `['organization_id', 'type']`
- Non-system presets: matched by `['organization_id', 'name']`

### 4.7 UI — What Changes

- Remove the **Code** column from the charge types list table entirely
- Remove the **Code** input from the Add/Edit charge type form entirely
- The form becomes: Name, Description, Applies To, Recurring — nothing else

## 5. The Levy Calculation

### 5.1 Budget-Based Approach

The property manager enters a total monthly target per fund. The system distributes it proportionally using PQ. This matches how AGM budgets work — trustees vote on a total, not a rate.

```
Unit Admin Levy   = (unit.pq / SUM of all unit PQs in estate) × estate.admin_fund_amount
Unit Reserve Levy = (unit.pq / SUM of all unit PQs in estate) × estate.reserve_fund_amount
```

The implied rate is derivable for reporting but never stored.

### 5.2 Full Worked Example

Estate: Barnato View, 47 units
Admin budget: **R80,000/month** | Reserve budget: **R20,000/month** | CSOS: **R40.50/unit**

PQ sum: `3.1076 + (46 × 0.8117) = 40.4458`

**Unit 101 (134 m², PQ 3.1076165908):**
```
Admin Fund Levy    = (3.1076 / 40.4458) × 80,000 = R6,147.00
Reserve Fund Levy  = (3.1076 / 40.4458) × 20,000 = R1,537.00
CSOS Levy          = R40.50 (estate-configured flat)
──────────────────────────────────────────────────────────────
Total              = R7,724.50
```

**Unit 115 (35 m², PQ 0.8117085408):**
```
Admin Fund Levy    = (0.8117 / 40.4458) × 80,000 = R1,605.00
Reserve Fund Levy  = (0.8117 / 40.4458) × 20,000 = R401.00
CSOS Levy          = R40.50
──────────────────────────────────────────────────────────────
Total              = R2,046.50
```

### 5.3 Rounding Correction

Individual unit levies round to 2 decimal places. The last unit receives a correction ensuring the sum of all unit levies equals the budget exactly. Applied in the billing run service, not in the model.

### 5.4 Override Rule

`levy_override` on a unit replaces the PQ-calculated admin levy only. Reserve levy is always PQ-based.

### 5.5 No-PQ Fallback

Units without `pq` get an equal share: `budget / total_unit_count`. Safety net only — flagged in the billing preview.

### 7.8 UnitService — Billing Run Logic

```php
$totalPq       = $estate->units()->whereNotNull('pq')->sum('pq');
$adminBudget   = (float) $estate->admin_fund_amount;
$reserveBudget = (float) $estate->reserve_fund_amount;
$units         = $estate->units()->with('owner')->get();
$runningAdmin  = $runningReserve = 0;
$lastUnit      = $units->last();

foreach ($units as $unit) {
    if ($unit->is($lastUnit)) {
        $adminLevy   = round($adminBudget   - $runningAdmin,   2);
        $reserveLevy = round($reserveBudget - $runningReserve, 2);
    } elseif ($unit->levy_override !== null) {
        $adminLevy   = $unit->levy_override;
        $reserveLevy = $totalPq > 0 ? round(($unit->pq / $totalPq) * $reserveBudget, 2) : 0;
    } elseif ($unit->pq !== null && $totalPq > 0) {
        $adminLevy   = round(($unit->pq / $totalPq) * $adminBudget,   2);
        $reserveLevy = round(($unit->pq / $totalPq) * $reserveBudget, 2);
    } else {
        $adminLevy   = round($adminBudget   / $units->count(), 2);
        $reserveLevy = round($reserveBudget / $units->count(), 2);
    }
    $runningAdmin += $adminLevy; $runningReserve += $reserveLevy;
    // Write line items: type=admin_levy → $adminLevy, type=reserve_levy → $reserveLevy
}
```

## 8. PQ Batch Import / Export

### 8.1 Export

**Route:** `GET /api/v1/estates/{estate}/units/pq/export`

Uses `PhpOffice\PhpSpreadsheet` (already installed). Returns `.xlsx` with columns: `unit_number`, `section`, `pq`, `size_sqm`.

### 8.2 Import

**Route:** `POST /api/v1/estates/{estate}/units/pq/import`

Accepts `.xlsx` or `.csv`. Matches rows by `unit_number`. Updates `section`, `pq`, `size_sqm`. Atomic — any failure rejects the whole file. Returns: updated count + failed rows with reasons.

## 10. Test Scenarios

### A — Full PQ, clean data
All 47 unit admin levies sum exactly to R80,000. Reserve levies sum to R20,000.

### B — PQs sum to 100 (certified SA scheme)
Unit PQ 3.1076 → `(3.1076/100) × budget`.

### C — Mixed (some units missing PQ)
PQ units use proportional formula. Missing-PQ units get equal-share fallback. Both visible in billing preview.

### D — levy_override set
Admin levy = override. Reserve levy still PQ-calculated.

### E — Reserve fund null
RESERVE_LEVY line item omitted. ADMIN_LEVY generates normally.

### F — CSOS: SA vs BWA
SA estate: CSOS prompt shown, appears on every invoice. BWA estate: no prompt, no CSOS line item.

### G — Import bad row
Any invalid row → whole import rejected, nothing saved, error list returned.
